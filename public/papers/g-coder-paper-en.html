G‑Coder: Architecture, Safety Invariants, and Formal Evaluation of Air‑Gapped Autonomous Software Engineering

Scientific & Technical Report — Security Invariants, Multi‑Agent Governance, and Methodology

Alfacan Defence Group Limited (Company No. 17062207) • Guardian Cloud Research Labs

Abstract. Generative language models applied to software engineering ("vibe coding") frequently produce syntactically valid yet security‑critical code that reproduces OWASP / CWE Top‑25 weakness patterns. This paper presents G‑Coder, an autonomous software‑engineering platform operating inside an air‑gapped security perimeter. We formalize its architecture around three constructs: (1) an interactive, observable multi‑agent Council; (2) two‑stage RAG grounding against curated OWASP / CWE doctrines; and (3) deterministic process invariants enforcing human‑on‑the‑loop authorization. We outline a formal evaluation methodology and address structural threats to validity. Empirical benchmarking is scheduled following GPU re‑activation post‑audit; no performance results are reported here.

1. Problem Formulation & Expected‑Loss Minimization

The direct deployment of generative LLMs in code synthesis accumulates structural vulnerabilities (SQLi, IDOR, race conditions, insecure deserialization) because token‑probability maximization ignores the underlying threat model. Existing commercial paradigms present a flawed trade‑off: streaming source code to external APIs (Copilot, Cursor) introduces confidentiality breaches, whereas server‑hosted cloud IDEs (Codespaces‑class) incur unsustainable compute overhead.

Rather than guaranteeing an unachievable zero‑defect target state (∀ s ∈ St : Violations(s, D) = ∅), we formalize secure automated software engineering as minimizing the expected number of security violations under a doctrine D, subject to a human‑supervised transition relation:

St  =  argminS  𝔼[ Violations(S, D) ] subject to   Si+1 = Apply(ΔSi)  ⇔  HumanApprove(ΔSi) = true

The guarantee is thus relocated from an (undecidable) property of the output code to verifiable properties of the process: every applied change transits an explicit human authorization gate (§3), and the objective is optimized by doctrine‑grounded review (§4) rather than asserted.

3. Safety Invariants

The architecture enforces four non‑negotiable process invariants:

  • Inv‑1 (Air‑Gap Domain Boundary). Proprietary source never leaves the internal perimeter. External validation defaults to false (EXTERNAL_VALIDATION_ALLOWED = false); enabling it requires explicit per‑client opt‑in, and egress is restricted to automatically sanitized snippets via sanitizeForExternal().
  • Inv‑2 (Human‑on‑the‑Loop Gate). A code modification ΔS transitions to APPLIED exclusively upon explicit verbal operator authorization in chat (e.g. "действуй"), which also constitutes the audit record.
  • Inv‑3 (Critical Risk Gate). Modifications rated CRITICAL are prohibited from autonomous application under all settings.
  • Inv‑4 (Governed Debrief Loop). Post‑execution lessons are anonymized and distilled back into the RAG doctrine index (human‑reviewed) for governed continuous self‑improvement; only sanitized patterns — never client code — are written back.

4. Doctrine Grounding (Two‑Stage RAG)

To suppress hallucinatory synthesis, the Reviewer validates candidate patches against a dedicated s-rag engine. Retrieval is two‑stage: (1) dense retrieval — a bi‑encoder recalls candidate rules K from the OWASP / CWE vector index by semantic similarity; (2) contextual re‑ranking — a cross‑encoder re‑scores candidates on joint codebase‑and‑threat‑model semantics before the top passages enter the prompt context. Enterprise clients may attach private per‑tenant collections (house standards, rules of engagement).

6. Limitations & Threats to Validity

  • Audit‑state execution. Primary AI inference runs on mock handlers while the GPU pool undergoes the pre‑launch security audit; no live‑model measurements are reported.
  • No empirical results yet. The metrics of §5 are proposed, not measured; the paradigm claim is architectural, pending the benchmark.
  • Registry constraint. The desktop fork uses OpenVSX (Microsoft's Marketplace is closed to forks), a smaller extension ecosystem.
  • Human‑latency dependency. End‑to‑end throughput is bounded by human response latency in the approval loop — an intentional trade of speed for governance.

7. Scale & Fleet Economics

By executing editor compute locally ($0 server cost) and offloading heavy build / deploy to client infrastructure via guardian-agent, G‑Coder targets an ~85% gross margin across the S1–S4 intensity tiers ($25–$100 / mo), without the Codespaces‑class compute overhead of server‑hosted IDEs.
